# ADR 0019 — One weight reader for the legacy stone format; canonical kg on every new weigh-in

- **Status:** accepted (Architect, 18 Nov 2026) · v2.32.2
- **Context:** weigh-ins have always been stored as one number in a "stones.pounds-digits" code (typed "14.68" and the Fitdays photo: 14st 6.8lb; the dot of the pounds removed), saved with `parseFloat`, so a lost trailing zero makes 14st 11.0lb (14.110) and 14st 1.1lb (14.11) the same number. Typed "14st 6lb" / "14:6" stores decimal stones. Screens read the code; the BMR, goals and target weight read the same numbers as decimal stones — 1–2 kg off for most weigh-ins (JC 5/5, Becks 3/3 in the 3 Nov backup).
- **Decision:** `src/lib/weight.js` `readWeight` is the ONLY reader (by digits after the dot: 1–2 = pounds below 10; 3 starting 10–13 = 10.0–13.9 lb; 4+ = decimal stones; 40+ = kg; an entry's `kg` always wins). Numbers that are genuinely ambiguous (x.1, x.11, x.12, x.13) are shown as before with "⚠ Check this weigh-in", never guessed. Every new weigh-in (typed, photo, history edit, import) ALSO stores `kg`, computed from the text as typed (zeros kept). Stored `v` values are never rewritten (ADR 0002); the display stays in stones.
- **Alternatives rejected:** rewriting stored values to kg (a migration on live data; a rollback would misread them); guessing ambiguous values (silent errors in health data).
- **Consequences:** BMR, goals, target weight and AI context now use the true weight (the backup's BMRs move by the 1–2 kg difference); old versions ignore `kg`. Typing "14.110" (with the zero) records 14st 11.0lb unambiguously.
